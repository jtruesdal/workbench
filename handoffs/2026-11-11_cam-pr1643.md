# cam-pr1643 handoff, 2026-11-11 (workstream complete)

ESCOMP/CAM PR #1643 (Jian Sun's "reduce memory usage in CAM init", plus the StormSPEED probe and a
true per-rank fallback) is in CAM as **`cam6_4_220`** (`00e7349f`, merge of `9c1d20b6`). The code is
identical to what was tested (tree `f893f2d0`, apart from `doc/ChangeLog`).

## History in short

- Branch on Jian's PR head `948c578c`: StormSPEED `44cb2d12` (probe + fallback) cherry-picked; the SHM
  system test (`87731ef2`, `af5051b1`) deliberately not taken into CAM.
- Izumi check with plain ESCOMP CAM: probe PASSED on GNU, FAILED on NAG and Intel -> not a StormSPEED
  artifact. Cause: MVAPICH2 version (GNU 2.3.7; Intel/NAG 2.3.3, whose `MPI_Win_shared_query` bug was
  fixed in 2.3.4). All three builds are `ch3:psm` with shared memory (`mpiname -a`).
- First fallback made every rank a one-rank "node" (MPI windows, serial read + broadcast in
  `tracer_data`). Replaced, for the CESM3 release, by a true fallback: the original per-rank data paths
  (plain allocate, PIO reads in `tracer_data` and `soil_erod_mod`, `mpicom` broadcasts); only additions
  are the init probe (skipped with `cam_shmem_force_private`) and freeing the tables at finalization.
- Base `cam6_4_219`; `aux_cam` on all four platforms bit-for-bit (NLFAIL only `stream_ndep_mapalgo`;
  derecho rttov pre-existing). GPU ne30 A/B (shared vs force_private): identical, same speed, so sharing
  stays on for GPU builds. CAM SE extra test before tagging: OK.
- Jian's branch: `cam_development` merged (`0356a7d6`), then sjsprecious/CAM#2 (4 commits) applied by
  fast-forward push (the user can push to the PR branch via "allow edits by maintainers" but cannot
  merge PRs in Jian's fork), ChangeLog commit `9c1d20b6`, merged and tagged.

## Comment for NCAR/StormSPEED#106

Cause found: the MVAPICH2 version on izumi, not the compilers or StormSPEED.

All three izumi MVAPICH2 builds are configured the same way for shared memory
(`--with-device=ch3:psm`, nothing disabled; checked with `mpiname -a`):

| Compiler | MVAPICH2 module | Version | cam_shmem probe |
|---|---|---|---|
| GNU 12.4.0 | `mpi/2.3.7/gnu/12.4.0` | 2.3.7 | PASSED |
| Intel 20.0.1 | `mpi/2.3.3/intel/20.0.1` | 2.3.3 | FAILED |
| NAG 7.0 | `mpi/2.3.3/nag/7.0` | 2.3.3 | FAILED |

The MVAPICH2 2.3.4 release notes (the release after 2.3.3) include "Fix bad baseptr address
returned from MPI_Win_shared_query" and "Add proper fallback and warning message when shared RMA
window cannot be created" -- exactly the symptom here (peers get no address from
`MPI_Win_shared_query`).

The same behaviour is seen with plain ESCOMP CAM (cam6_4_218/219 + PR #1643). In the CAM version
(ESCOMP/CAM#1643) the fallback now runs the original per-rank code paths (plain allocate, per-rank
PIO reads); izumi NAG `aux_cam` is bit-for-bit with cam6_4_219 that way.

Building the izumi Intel/NAG stacks against MVAPICH2 >= 2.3.4 (e.g. 2.3.7, as for GNU) should let the
probe pass there too; that is a request for the CGD system administrators, not a code change.
