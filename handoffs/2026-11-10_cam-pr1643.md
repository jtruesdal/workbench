### 1. PR description

## Node-shared tables: probe plus a true fallback to the original code

For ESCOMP/CAM#1643. Based on `fix_ne1024_init_oom` after its update to `cam_development`
(= `cam6_4_219`, merge `0356a7d6`), so this PR contains only the four commits below.

### Why
On izumi with the MVAPICH2 builds used by NAG and Intel, `MPI_Win_allocate_shared` succeeds but
`MPI_Win_shared_query` gives non-leader ranks no address (size 0, null pointer). The node-shared
tables in `phys_prop`, `mo_jlong`, `soil_erod_mod` and `tracer_data` are then null on all but one
rank per node. First seen in StormSPEED (NCAR/StormSPEED#106); reproduced with plain cam6_4_218 +
this PR.

Cause: MVAPICH2 version. All three izumi MVAPICH2 builds use `--with-device=ch3:psm` with
shared-memory support (`mpiname -a`); GNU uses 2.3.7 (probe passes), Intel and NAG use 2.3.3
(probe fails). The MVAPICH2 2.3.4 release notes list "Fix bad baseptr address returned from
MPI_Win_shared_query" and "Add proper fallback and warning message when shared RMA window cannot
be created". The probe therefore protects CAM against MVAPICH2 < 2.3.4 (and any other MPI whose
shared windows do not work).

### Changes
- `cam_shmem_mod`: at init, a small collective probe allocates a shared window and checks that every
  rank can see it. If it fails, node-shared memory is off and CAM uses the **original per-rank code
  paths**: `cam_shmem_alloc_*` is a plain `allocate`, `cam_shmem_fence` does nothing,
  `cam_shmem_free` deallocates, `cam_shmem_leader_comm` is `mpicom`, and `tracer_data` and
  `soil_erod_mod` read through PIO on every rank as before (new query `cam_shmem_enabled()`).
  No MPI-3 window is used in that mode. The atm log reports `probe PASSED` / `probe FAILED` and the mode.
- New namelist `cam_shmem_nl` / `cam_shmem_force_private` (default `.false.`): a fail-safe that
  selects the original per-rank code paths (the probe is then skipped, so no MPI-3 window is created).
  No default entry, so it is not written to atm_in unless set in user_nl_cam.
- `cam_shmem_init` is called after `read_namelist`.

Node-shared memory stays on by default wherever the probe passes.

### 3. Comment for NCAR/StormSPEED#106

Cause found: the MVAPICH2 version on izumi, not the compilers or StormSPEED.

All three izumi MVAPICH2 builds are configured the same way for shared memory
(`--with-device=ch3:psm`, nothing disabled; checked with `mpiname -a`):

| Compiler | MVAPICH2 module | Version | cam_shmem probe |
|---|---|---|---|
| GNU 12.4.0 | `mpi/2.3.7/gnu/12.4.0` | 2.3.7 | PASSED |
| Intel 20.0.1 | `mpi/2.3.3/intel/20.0.1` | 2.3.3 | FAILED |
| NAG 7.0 | `mpi/2.3.3/nag/7.0` | 2.3.3 | FAILED |

The MVAPICH2 2.3.4 release notes (the release after 2.3.3) include "Fix bad baseptr address
returned from MPI_Win_shared_query" and "Add proper fallback and warning message when shared RMA
window cannot be created" -- exactly the symptom here (peers get no address from
`MPI_Win_shared_query`).

The same behaviour is seen with plain ESCOMP CAM (cam6_4_218/219 + PR #1643). In the CAM version
(ESCOMP/CAM#1643) the fallback now runs the original per-rank code paths (plain allocate, per-rank
PIO reads); izumi NAG `aux_cam` is bit-for-bit with cam6_4_219 that way.

Building the izumi Intel/NAG stacks against MVAPICH2 >= 2.3.4 (e.g. 2.3.7, as for GNU) should let the
probe pass there too; that is a request for the CGD system administrators, not a code change.
